# めししるべ 開発ログ

## 概要

「めししるべ」は、今夜のお店選びで迷ったときに、条件に合う候補を3店にしぼって提案するWebアプリ。

エリア、検索範囲、料理ジャンル、シーン、予算、来店日時、除外ワードを指定して、Google Places APIとHotPepper APIを使って候補を集める。最終的には「たくさん探す」よりも「迷いを減らして決めやすくする」ことを重視する。

## ブランド

- ブランド名は「めししるべ」。
- ロゴは「道しるべ」「3つの候補」「現在地」をモチーフにした。
- 白い曲線は目的地へ向かう道。
- 金色の3つの丸はおすすめの3店舗。
- 金色の四角は現在地。
- 黒背景でも白背景でも使えるように調整した。
- favicon用には、円を外した超簡略版も用意した。

## 主な機能

- 現在地またはエリア指定で検索できる。
- 検索範囲は500m、1km、2km、5kmから選べる。
- ジャンルはプリセットと自由入力の両方に対応。
- シーンはデート、女子会、接待、記念日、23時以降などを指定できる。
- 来店日時は日付と時間を指定できる。
- 時間はデフォルトでは指定なし。必要なら「現在時刻」ボタンで現在時刻を入れられる。
- 予算を複数選択できる。
- 除外ワードを指定できる。
- 検索結果は評価をもとに並べ、上位3件を提案する。
- 店舗カードからGoogle Mapsを開ける。
- 結果から不要な店を除外して次の候補を見られる。

## 検索ロジック

- 検索本体はVercel Functionsの `/api/search` 経由で実行する。
- Google Places APIとHotPepper APIを併用する。
- Google Places APIで候補を取得し、HotPepperの情報で予約URLや予算情報を補完する。
- 除外ワードはGoogle結果とHotPepper照合結果のテキストに対して適用する。
- 除外ワードで「もんじゃ」を指定したとき、HotPepper側の検索結果も照合して除外できるようにした。
- 以前はGoogle候補が10件未満の場合、中心地点を東西南北にずらして追加検索していた。
- 2026-05-31時点で、自動の東西南北追加検索は停止した。候補が3件未満の場合は、ユーザーが明示的に検索範囲を広げるUIに変更した。
- 検索範囲5kmを追加し、サーバー側でも最大5000mまで通るようにした。

## APIと安全対策

- Google Places APIキーはブラウザ側で見える前提の公開キーとして扱う。
- Google Cloud側でHTTPリファラー制限を設定する。
- 本番URLとローカル開発URLのみ許可する。
- 検索本体はサーバー側 `/api/search` に寄せ、HotPepper APIキーはサーバー側で扱う。
- 1IPあたりの検索回数制限を入れた。
- 短期制限は10分で5回。
- 長期制限は24時間で30回。
- Google Cloudの割り当て、使用量、請求アラートを確認する運用にした。
- Google Cloud無料トライアルの残高低下通知をきっかけに、請求レポートを確認した。
- 2026年5月時点で、費用の主因は `Places API Text Search Enterprise + Atmosphere` だった。
- Google Cloud Billingの実績では、2026年5月に `Places API Text Search Enterprise + Atmosphere` が7,636回で約42,026円、`Places API Place Details Photos` が6,287回で約5,841円だった。
- `Autocomplete Requests` は3,246回、`Places API Text Search Pro` は57回で、この時点では費用0円だった。
- 主なボトルネックはAutocompleteや地図ではなく、Google Text Searchの高額SKUと呼び出し回数だった。
- `editorialSummary` は高額SKUに寄るため検索レスポンスから外した。
- `servesLunch` / `servesDinner` も高額SKUに関わるが、外すとカラオケなど食事目的ではない候補が混ざり、検索精度が落ちたため戻した。
- 今後も費用を下げる場合は、Google Places APIの高額フィールド削減だけでは限界があるため、キャッシュ、追加検索回数の抑制、検索条件ごとの再利用を検討する。
- 実API検証の安全対策として、Google Cloud側で `SearchTextRequest per day` を50、`GetPhotoMediaRequest per day` を100に制限した。
- ローカル検証用に `VITE_MOCK_SEARCH=true` を追加した。500mでは2件、1km以上では3件のモック結果を返し、Google APIを叩かずに「範囲を広げる」UIを確認できる。
- ローカルのVite開発サーバーでは、`.env` 読み込み前にAPIキーを固定しないよう、`api/search.js` 側で環境変数をリクエスト時に読む形へ変更した。

## UI/デザイン

- 黒背景を基調に、白と金をアクセントにした。
- タイトルロゴは日本語の「めししるべ」を採用。
- フォントはタイトルだけでなく、UI全体も日本語と英語で見やすいものに調整した。
- スマホ表示では、ロゴとタイトルの比率が自然になるよう調整した。
- X共有時のOGP画像を新しいロゴに更新した。
- OGPから不要な説明文と装飾線を外して、シンプルにした。

## 公開

- Vercelで公開。
- 公開URLは `https://meshishirube.vercel.app/`。
- Google CloudのAPIキー制限には、本番URLとローカルURLを登録した。
- Xでの告知に向けて、OGP画像、favicon、ロゴ、スマホ表示、API利用制限を調整した。

## 開発メモ

- GPT/Codexと相談しながらAI駆動で開発した。
- ロゴ案の検討、UI調整、検索ロジック、API制限、OGP、公開設定まで一通り実施した。
- 開発の方向性は「条件に合う候補をたくさん出す」よりも「今夜決めやすい3店にしぼる」こと。
- 地方や郊外では候補が少なくなりやすいため、5km検索や10件未満時の追加検索を追加していた。
- ただし実費では追加検索によるGoogle Text Search回数の増加が大きかったため、自動追加検索はやめ、候補不足時のみユーザー操作で範囲を広げる方針に変更した。
- 今後の改善時は、候補数の厚みよりも「3件提案として成立する品質」とAPIコストのバランスを見る。
- 会社Teamsで告知したところ、Vercel Analytics上で約845 visitors、3,476 page views程度まで伸びた。
- `/search` と `/results` への到達率が高く、初見でも使い方は比較的伝わっていた。
- 流入は主にTeams由来で、デスクトップ/Windows比率が高かった。
- API費用を抑えるために `types` / `primaryType` を使ったフィルタを追加した。
- 通常検索ではレストラン系タイプを中心にし、カフェ、バー、テイクアウト系はジャンルで明示されたときだけ通す方針にした。
- `karaoke` / `night_club` は通常検索では除外する。
- 精度とコストはトレードオフが大きい。現状は、精度を守るために `servesLunch` / `servesDinner` を戻しつつ、`editorialSummary` は外した状態。

## 2026-05-31 費用削減・検証タスク

優先順位は以下。

1. 自動追加検索を止める。
   - 対応済み。
   - `api/search.js` の東西南北オフセット検索を削除した。
   - 候補が0件または1〜2件の場合、結果画面に次の検索範囲へ広げるボタンを出すようにした。
2. 実検索レビュー。
   - Google Cloud側で `SearchTextRequest per day = 50`、`GetPhotoMediaRequest per day = 100` に制限済み。
   - 本番は `SEARCH_DISABLED=true` のまま維持し、ローカルだけ実APIで確認する。
   - 確認シナリオ例: 新宿500mジャンルなし、新宿1kmイタリアン、渋谷1kmデート、梅田1km居酒屋、地方駅1kmジャンルなし、カフェ1km、記念日1km。
3. 検索ログを入れる。
   - 検索回数、Google Text Search呼び出し回数、結果件数、範囲拡大ボタン押下回数、カフェ/記念日の2本検索回数を計測したい。
4. カフェ/記念日の2本検索を見直す。
   - まだGoogle Text Searchが2回走る条件なので、実検索レビュー後に必要性を判断する。
5. チェーン店表示設定を検討する。
   - ファミレス、牛丼、ファストフード、大手カフェなどのリーズナブルなチェーンを「こだわり店中心」「バランス」「チェーンも歓迎」などで扱えるようにする案。
   - 最初はGoogleデータを保存せず、めししるべ側の有名チェーン名リストでスコアを下げる/除外する方式が現実的。
6. 写真を1位だけ、または遅延表示にする。
   - `Place Details Photos` が2番目の費用要因だった。
7. 営業時間/ランチ・ディナー系フィールドを見直す。
   - `servesLunch` / `servesDinner` / `regularOpeningHours` は体験に効くが高額SKU要因なので、品質低下と費用削減の両面で検証する。
8. 無料検索回数制限を入れる。
   - 公開再開前には必須。スタミナ制/チケット制はアイデアとして保留。
9. マネタイズ実験。
   - スタミナ、追加検索チケット、サブスク、予約送客など。原価が見えてから検討する。
